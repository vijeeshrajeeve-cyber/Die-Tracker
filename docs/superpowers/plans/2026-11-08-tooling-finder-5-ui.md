# Tooling Finder, Plan 5 of 5: The UI — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Put the finder in front of people: a **New die order** top-bar button that opens a Prepare New Die Order PDF form with a **Find tooling** panel (candidates with overlay, similar profiles, *Use this* fills the tooling fields, Generate stamps and records the form), the same panel inside the Backup Die Requests generate modal, and a **Toolings** page (master list, detail drawer with the drawing and the extracted opening, review queue for uncertain openings and flagged profile pictures, edit controls, Add tooling with drawing upload).

**Architecture:** Server first: a `new_die_order_forms` table and a `users.can_review_toolings` flag (schema written twice, parity-tested); write routes on `/api/toolings` (edit, review an opening, add a tooling with a drawing that runs Plan 2's extractors), a review route on `/api/profile-shapes`, a `trace` route that turns the form's profile PNG into a true-size polygon with Plan 3's `shapeFromProfilePng`, and `/api/new-die-order-forms` that stamps the drawing with the backup flow's generator and records the form. Client second: one reusable `FindToolingPanel` (SVG overlay from the finder's `pockets` + `placements`), a `NewDieOrderModal` built from the backup modal's field set and prefill rules, a small insertion into the backup modal, the `ToolingsPage` modelled on the Frozen Designs registry, and the sidebar/top-bar wiring. Every cache the finder or similarity index holds is invalidated by the routes that change their inputs.

**Tech Stack:** Node 20 CommonJS (`.cjs`), Express 5, `multer` (already used), `pdf-lib` via `dieOrderTemplate.cjs`, Postgres via `pg`, `node:test`; React 18 ESM client with inline styles and `lucide-react` icons as the rest of `src/`. **No new npm dependencies.** No browser test framework exists: pure client helpers are tested with `node:test`, components are smoked in the browser on the test server.

**Spec:** `docs/superpowers/specs/2026-11-07-tooling-finder-design.md` — parts 6 and 7 are this plan's slice; Goals (first three bullets), Non-goals (no order creation; backup flow unchanged beyond the panel), Anti-goals (uncertain geometry visibly marked and never above confirmed; "opening not known" shown, never guessed; the manual path kept), "My calls" (backup form gets the same panel and shows the die's current tooling; unknown typed numbers become `unverified`; who reviews; similarity strip shows 8; generated form PDFs under the tooling storage root). Mockup the user chose (option A): `.superpowers/brainstorm/375-1794074743/content/finder-placement.html` — a result card per candidate (number, kind · size · cavities, a small overlay SVG, tags "Clears by 6.8 mm" / "Chart: allowed P7 / 250x140" / "Rack B3", "Used by …", geometry source + confidence, *Use this*), greyed cards with the reason for similar-only toolings, and a "Similar existing profiles" strip of small cards (die, tooling, press · size · cav).

## Global Constraints

- Server code is CommonJS in `server/**/*.cjs`; tests `*.test.cjs` beside the module, run by `npm test` (baseline on main a8c88a5: 1454 pass / 2 skipped). Client code is ESM under `src/`, inline styles + theme object + `lucide-react` icons like its neighbours; pure client helpers in `src/utils/*.js` with `*.test.js`. **No new npm dependencies.**
- Every schema change is written **twice** (`init.sql` and the migration in `server/db.cjs`), `CREATE TABLE IF NOT EXISTS` / `ALTER TABLE … ADD COLUMN IF NOT EXISTS`, and covered by `server/services/toolingSchema.test.cjs`.
- **Who may do what:** anyone with access to the Backup Die Requests page or the Orders page can run the finder and generate a new die order form; the Toolings page is visible to admins and to users whose `page_access` includes `toolings`; **review actions** (confirm/correct/mark-none an opening, retire or reactivate a tooling, change its location or size class, add a tooling, clear a profile picture's review flag) need `req.user.role === 'admin'` or `users.can_review_toolings = true` (`reviewerMiddleware`). Admins always can; the flag is forced false for admins like `can_edit_order_details`.
- **No order is created** by the new form. Generating records a `new_die_order_forms` row and `die_tooling_links` rows (source `new-order-form`) only.
- **Unknown tooling numbers** typed into either form become `toolings` rows with `status 'unverified'`, `source 'order-form'`, kind from `parseToolingNumber`, no geometry — the finder never suggests them until a reviewer confirms (sets status `active`).
- **Overlay rendering:** SVG only, from the finder's `pockets`, `query.profile.points` and `placements` — no raster; the profile drawn after `theta` then `(tx, ty)`; y flipped for screen; one SVG per candidate card at about 90 × 60 px with a `viewBox` fitted to the pocket bbox + 10 %.
- **Visible honesty:** every candidate card shows the geometry source and confidence (`confirmed` / `likely` / `uncertain`, with `uncertain` in the warn style and a "needs review" tag); `needsTransfer: true` shows "held at PRESS n, needs transfer"; `null` shows "location unknown"; `clearanceCapped` shows "> 50 mm"; `chart.basis 'no_chart'` shows a banner "No combination chart for this press — chart gate not applied"; similar-only toolings are greyed with their `reason` text, never hidden; a tooling with no opening says "opening not known". The INSERT/BOLSTER fields stay plain text inputs.
- **Use this** fills exactly one pair: `INSERT_NO` + `INSERT_SIZE` for an insert, `BOLSTER_NO` + `BOLSTER_SIZE` for a bolster; the other pair is untouched; a second *Use this* on the other kind fills the other pair. The chosen candidate is remembered for the form record (`chosen_tooling`, `chosen_from_finder: true`); typing over the field afterwards sets `chosen_from_finder: false`.
- **Similarity strip** shows the 8 nearest dies (API returns 20); each card: die number, its toolings (number + a scope/chart tag), press · die size · cav from the die list when known.
- Scripts and routes never run an unscoped `DELETE`; review routes never touch geometry they were not asked to change; every route that changes `toolings`, `tooling_openings` or `profile_shapes` calls `toolingFinder.invalidate(plant)` and/or `profileSimilarity.invalidate(plant)`.
- Commit after every task; messages end with `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>`.

## Review Focus

1. A posted drawing whose profile has no defensible scale (no `SCALE`, no CCD) must reach the form as similarity-only: the Find tooling button is disabled with the reason "profile size unknown — fit needs a scale or CCD", never a fit on a guessed size — Task 3 test `trace without scale answers true_size false` and Task 5 helper test `finder readiness explains why it cannot run`.
2. *Use this* on a bolster after *Use this* on an insert fills the bolster pair and leaves the insert pair as it was — Task 5 test `applyChoice fills one pair and keeps the other`.
3. A reviewer who marks an opening `none` must not lose the drawing or the tooling: only `tooling_openings.confidence`/`pockets` change and the finder cache is invalidated — Task 2 test `mark none clears pockets, keeps the tooling and drawing, invalidates`.
4. A non-reviewer calling any review route gets 403, and the Toolings page hides the edit controls for them — Task 1 test `reviewerMiddleware: admin passes, flagged user passes, plain user 403` and Task 6 drawer rendering check in the browser smoke.
5. Generating the form with a typed unknown insert number creates an `unverified` tooling and a link, and the finder still never returns it — Task 4 test `unknown typed number becomes unverified and linked` and Task 4 ⚠️ check against `CANDIDATE_SQL` (`status = 'active'`).
